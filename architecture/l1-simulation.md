# L1 仿真层：确定性的基建物理世界

> 文档状态：核心稳定，校准未闭合
> 适用版本：closure v0.1.0
> 读者：想用确定性基建世界做评估/回归的开发者；想修改物理、技能、订单、制造、心情模型的开发者
> 前置知识：mower 排班表 JSON 的基本结构；HTTP JSON 调用
> 相关代码：`ui/src/riic/riic-sim/`（TypeScript），公开入口见附录 B

L1 重建了明日方舟基建的物理过程，并保证同输入同输出。它只回答"给定当前世界和操作，接下来物理上会发生什么"，不做任何排班决策。读完快速开始即可建会话、读状态、推进时间；需要判断结果可信度时，再看可靠性章节的适用域与论证。

L1 是仿真模型，不提供真实游戏接入或账号操作；数值是模型估计，不是游戏内产出承诺。

## 1 这套能力解决什么问题

设备侧基建评估慢、不可复现、异常难构造（背景见[导读](README.md)）。L1 把基建物理搬进一个确定性世界：

- 订单生成与交付、制造批次与仓库、心情消耗与涣散、无人机充能与加速、技能效率求值，全部按固定规则推进；
- 引擎内部不读墙钟、不用未播种随机，同一份排班与操作序列重复运行，事件流、库存、快照完全一致；
- 推进量由调用方决定：一小时、一天、一周都可以在秒级算完。

L1 不负责：何时换班、跑哪一单、无人机投给谁（这些决策由 mower 本体在 [L2 执行层](l2-execution.md)中做出）；虚拟时钟与设备操作（属于 L2）；候选排班搜索与排名（属于 L3，开发中）。

## 2 你能用它做什么

- **业务回归的底座**：配合 L2，让 mower 真实业务在固定世界里反复运行，比较改动前后的产量、漏单、涣散与任务轨迹；
- **机制实验**：调整技能、产物、布局或初始心情，观察日级产出指标变化，不必等设备侧；
- **异常构造**：把初始库存设为赤金不足、把心情设为接近涣散、关闭自动收取制造满仓，主动复现设备侧靠运气遇到的场景；
- **修改物理与技能模型**：订单、制造、心情、无人机各模块边界清晰，改动后跑定向测试即可验证（见第 7 章）。

适用范围：需要"可复现的相对比较"时，L1 当前即可用；需要"跨布局、跨干员池的绝对产量保证"时，先读第 6 章的适用域——校准尚未闭合，绝对数字只在已验证范围内可信。

## 3 核心概念与数据流

### 3.1 世界状态：从排班表零转换构建

L1 直接消费 mower 的排班表 JSON（`plan1` + `facility_levels` + `advanced_settings` + `conf` + `backup_plans`），不需要额外格式适配。世界包含：

- **房间**：9 个左排生产格、控制中枢、会客室、办公室、加工站、训练室、回收站与 4 间宿舍。静态设施无条件创建；生产房与宿舍只在排班表声明时创建，槽位数由排班表决定。每个槽位持有一条轮换链（主班 + 替补序列）；
- **干员**：心情（0–24）、涣散标记、当前占位。初始心情默认满值，可用 `initialMoods` 覆写（暖启动）；
- **订单**：逐笔建模，含档位（2/3/4 条赤金）、到达时刻与状态。订单在生成瞬间按当时在岗的跑单干员"烘焙"实际赤金消耗与龙门币报酬（跑单快照），之后不随换人变化；待交付订单不会被每日刷新清空；
- **库存**：赤金、龙门币、经验、源石碎片、合成玉及材料计数；
- **无人机**：上限 250 架，自然充能 6 分钟/架，发电站技能可加速；1 架加速 = 生产/订单进度提前 3 分钟；
- **制造队列**：每房的批次进度、仓库占用与收取策略；
- **电力**：逐房计算发电与耗电并透出，供 mower 侧拒绝非法布局；物理层本身不据此停产。

训练室房间与占位存在，但专精训练产出不建模。

### 3.2 时间推进：定步长，事件只记录

L1 按固定步长逐块推进，默认步长 60 秒，效率每 5 分钟重算一次；步长是 L1 引擎内部选项，当前桥会话不暴露。任意推进量被切成不超过步长的块，每块内按固定阶段顺序结算：到期收取 → 日界判定 → 心情推进 → 涣散检测 → 效率重算与生产/贸易结算 → 无人机充能与部署 → 快照。桥模式下不运行内置调度，换班等决策全部来自外部。

日界落在每日 04:00：仿真原点 0 对应 04:00 日刷后的瞬间。日刷只触发日结算与事件，不清空待交付订单。

事件的角色是**记录而非驱动**：状态演化完全由阶段结算完成，事件流是它的可观测投影，供 L2 排空消费。因此接口与状态的时间戳精度是 1 毫秒，而事件的时间分辨率等于步长（默认 60 秒）。把步长调小可以提高心情/效率耦合与事件时刻的精度，代价是步数线性增长。

### 3.3 随机性：没有随机源，只有状态哈希

引擎代码不使用 `Math.random`，也不读取 `Date.now`。所有"看起来随机"的行为都是确定性选择：

- **订单档位抽签**：由订单序号与到达时刻做哈希，按当前档位概率的累积分布取档；
- **跑单预等待**：在 4–7 分钟区间内按订单序号哈希取值，模拟设备侧读单节拍差异；
- **线索面板**：可注入种子的伪随机序列，同种子同输入逐事件复现。

这些是**哈希选择子，不是概率采样器**：同输入必同输出，但长程序列不保证服从标称概率分布。订单档位构成与真实分布的偏差是已知经验误差来源（见 6.4）。

### 3.4 技能求值

技能求值独立于模拟循环，消费预计算的技能数据（覆盖 438 名干员、944 个技能阶段），按效果分量与条件族求值，输出逐房效率。副表条件是结构化表达式树的递归求值，不使用 eval 或动态构造；未建模的条件族保守判为不满足——方向是低估效率，而非虚高。

### 3.5 数据流

```text
排班表 JSON ──/session──▶ 世界构建 ──▶ 定步长推进
                                         │
外部写操作（换人/切产物/加速/充能）────────┤ 按设备耗时推进时钟
                                         ▼
                    /state 全量状态   /events 事件流   /collect 收取
```

读操作不耗时、不改状态；写操作先改世界，再按设备耗时推进时钟。设备耗时取固定常量（按设备侧 P95 口径标定），识别与点击默认成功——仿真日志因此比设备侧记录"干净"，这是设计取舍，代价见 6.4。

## 4 快速开始（最小可运行示例）

以下命令与路径随 v0.1.0 代码发行提供；当前 docs-only 提交不包含代码。

这些命令仅用于本地开发与仿真测试，不构成真实游戏接入教程；不提供 ADB、模拟器、账号或游戏客户端配置步骤。

### 4.1 启动桥服务

L1 桥是 TypeScript 服务，源码运行：

```bash
cd ui
npm ci
npx vite-node src/riic/riic-sim/bridge/server.ts
```

这段命令安装前端依赖并启动 L1 桥，默认监听 `127.0.0.1:5900`。健康检查：

```bash
curl http://127.0.0.1:5900/health
```

返回 `{"ok": true, ...}` 即服务就绪。

### 4.2 建会话、读状态、推进一天

以下 Python 脚本用标准库完成最小闭环：把一份排班表交给 `/session` 建会话，用 `/state` 读初始世界，用 `/advance` 推进 24 小时，再读一次状态对比库存。

```python
import json, urllib.request

BASE = "http://127.0.0.1:5900"

def post(path, payload):
    req = urllib.request.Request(
        BASE + path, data=json.dumps(payload).encode(),
        headers={"Content-Type": "application/json"})
    with urllib.request.urlopen(req, timeout=60) as r:
        return json.loads(r.read())

# 建会话：plan 直接用 mower 的排班表 JSON；externalScheduler 关闭内置调度
plan = json.load(open("config/plan.json", encoding="utf-8"))
sid = post("/session", {"plan": plan, "externalScheduler": True})["id"]

# 读初始状态：逐房驻员/心情/效率、全员心情、库存、无人机、电力
before = post("/state", {"id": sid})

# 推进 24 小时（毫秒）；期间只跑物理，不做换班决策
post("/advance", {"id": sid, "ms": 86_400_000})

after = post("/state", {"id": sid})
print("时钟:", before["clock"], "→", after["clock"])
print("库存变化:", {k: after["inventory"].get(k, 0) - before["inventory"].get(k, 0)
                    for k in after["inventory"]})

# 排空这一天的物理事件（订单到达/交付、批次完成、涣散、日界等）
events = post("/events", {"id": sid})["events"]
print("事件数:", len(events))

post("/close", {"id": sid})
```

`config/plan.json` 换成你自己的排班表即可。会话参数支持 `initialMoods`（覆写初始心情）、`initialInventory`（覆写初始库存）、`autoCollect` / `autoCollectIntervalMs`（收取策略）、`skillPool` 等；步长属于引擎内部选项，当前 HTTP 会话不暴露。完整端点见附录 B。

注意：桥模式下 L1 不做换班决策，干员心情耗尽后会涣散停产。要跑"有决策的完整基建流程"，用 [L2 执行层](l2-execution.md)的快速开始。

## 5 对外契约与稳定边界

L1 通过 HTTP JSON 桥（默认 `:5900`）对外提供会话与物理操作。稳定契约如下：

**读写语义**

- 读操作不耗时、不改状态：`/state` 读全量世界状态，`/events` 排空事件缓冲，`/health` 健康检查；
- 写操作按设备耗时推进时钟：`/arrange` 换人、`/product` 切产物、`/drone` 加速、`/fia` 充能；`/advance` 显式推进指定量；
- `/collect` 收取与 `/worldconf` 同步副表物理名单只改世界、不耗时；
- `/session` 建会话、`/close` 释放会话。

**数据格式**

- 输入排班表与 mower 的 `plan1` 格式一致，零转换；
- `/state` 返回毫秒时钟、可读时钟（`D<n> HH:MM`）、天数、逐房状态（槽位名单、驻员心情、订单倒计时、效率）、全员心情、库存、无人机数与电力；
- 事件为 `{ms, type, detail}` 序列，时间戳精度 1 毫秒，分辨率等于步长；
- 换人名单中 `Current` 表示保持现状，空串表示清空。

**版本语义**

- 端点路径、读写语义与状态字段属于稳定契约，变更需兼容性说明；
- 技能数据与物理常量的数值调整属于校准范畴，不改变端点契约，但会改变产量结果——依赖绝对数字的调用方应关注文档适用域更新；
- 桥客户端由 L2 提供（`sim_bridge/client.py`），对传输失败重试一次；重试语义与代价见 [L2 文档](l2-execution.md)第 6 章。

完整端点表与公开代码入口见附录 B。

## 6 可靠性、限制与失败模式

**确定性、资源守恒、容量硬上界是结构性质，由代码构造保证；产量误差是经验拟合，只在已验证适用域内有数据支撑。** 使用 L1 做决策时，先分清依赖的是哪一类结论。

### 6.1 确定性对开发者意味着什么

同一排班、同一初始心情与库存、同一操作序列与推进量、同一时钟纪元，L1（配合 L2）的输出——事件流、库存、快照、任务轨迹——唯一。这意味着：

- 回归可以用"重复运行结果一致"作为断言；
- 两份运行的差异可以逐事件定位到首个分叉点；
- 产量差异可以归因到排班或配置本身，而不是运行时序。

完整前提与残余缺口见 6.2 的论证；快速自检方式是用 L2 的回放工具重复运行并比较三个哈希（见 [L2 文档](l2-execution.md)）。

### 6.2 形式化模型与三条论证

把桥模式下的 L1 定义为离散时间系统 $\mathcal{M} = (S, E, \delta, s_0)$：

- **状态空间** $S$：元组 $(t, \{room_i\}, \{op_j\}, Inv, D, Q, B)$。$t$ 为毫秒时钟；$room_i$ 含槽位占位、产物、批次/订单进度、订单队列、仓库占用；$op_j$ 含心情、涣散标记、占位；$Inv$ 为库存向量；$D$ 为无人机数与充能进度；$Q$ 为任务队列（桥模式下为空）；$B$ 为副表索引。
- **操作字母表** $E$：外部写操作 `{arrange, product, drone, fia, worldconf, collect, advance}`（与桥端点一一对应），以及物理事件集合 `{batch_complete, order_arrive, order_deliver, exhaust, day_boundary, drone_deploy, stall, …}`。
- **转移函数** $\delta$：单步结算的固定阶段复合。耗时写操作 $a$ 的语义为 $\delta_a(s) = \text{bridgeAdvance}(cost(a)) \circ apply(a)(s)$——先改世界，再按设备耗时推进时钟；`collect`、`worldconf` 只改世界不推进时钟，`advance` 只推进时钟；读操作不耗时、不改状态。
- **初始状态** $s_0$：由排班表构建世界，加 `initialMoods`/`initialInventory` 覆写，$t=0$（04:00）。

这是**定步长离散时间系统**，不是连续时间离散事件系统；下面的"不漏产出"论证按定步长语义成立，不能套用事件队列的论证。

**引理 1（阶段确定性）。** 给定状态 $s$ 与步长 $dt$，单步结算的输出状态与事件序列唯一。

*证明思路。* 逐阶段检查：各阶段均为纯状态函数，无 I/O、无墙钟读取、无未播种随机（3.3 节）；房间遍历顺序由固定的房间键插入序决定；效率重算只依赖状态与固定间隔；订单抽签只依赖订单序号与到达时刻；心情推进是确定性线性公式加夹取。因此整个复合函数对同一输入给出同一输出。*假设*：技能数据文件与排班 conf 在运行期不变；浮点运算在同一平台同一运行时下逐位一致。∎

**引理 2（定步长不漏产出）。** 设步长为 $h$。制造与贸易进度按 $eff \cdot dt$ 连续累积，结算循环在步内结清全部到期批次与订单。因此任意推进量下都不会丢失产出事件；步长只影响事件时间戳的盖章时刻，误差不超过 $h$。

*证明思路。* 进度单调累积，结算以配方时长为模递减，循环次数只取决于累积进度与配方，与 $h$ 无关。把 $h$ 减半，只是把同样的产出分摊到更多步里结算，总量不变。订单到达另有亚步回推（剩余进度 ÷ 当前效率），其时间戳误差小于 $h$。∎

由此得到步长选择的工程结论：不存在事件跳跃模型意义上的"漏事件"风险；真正受步长影响的是三类耦合精度——心情在步内一次性结算（涣散时刻误差 $\le h$）、效率重算间隔带来的滞后（最多一个重算间隔）、事件时间戳分辨率（$= h$）。默认 60 秒对日级产出指标足够；需要逐秒对齐机制（如暖机爬坡曲线）时显式调小步长。同刻多事件的排序是全序且固定的：先按阶段序，同阶段内按房间插入序。

**引理 3（资源守恒）。** 对任一资源 $r$，记事件流中该资源的增量之和为 $\sum_e \delta_e(r)$，则

$$Inv_r(t_{end}) = Inv_r(0) + \sum_{e \in events} \delta_e(r)$$

即期末库存等于期初库存加全部事件增量。

*证明思路。* 所有库存变更都发生在生产、交付、搓玉、扣料四类结算点，每一处变更与一条携带对应增量的事件成对写出；日结算按事件增量求和而非重新盘点库存。等式由构造成立：库存是事件增量的积分，日结算是事件增量的分段积分，两者同源。∎

*例外*：引擎内部理论模式 `allowDebt = true`（当前桥会话不暴露）时赤金/碎片允许为负，"库存非负"被显式关闭，但守恒等式仍成立——负债只是放开非负约束，不改变记账结构。跑单快照的金额在订单生成时烘焙、交付时按烘焙值结算，不存在二次加价。

**确定性的三层论据与残余缺口。** 命题"同输入同输出"的论据分三层：① 无未播种随机——引擎全量代码不含 `Math.random` 与 `Date.now`，可由字面检索直接验证；② 无墙钟依赖进入决策——L1 不读真实时间，L2 侧只替换调度用时钟，真实单调时钟仅用于防自旋保护，不参与决策；③ 无并发竞态——桥会话单进程顺序处理，L2 用全局锁串行化，多候选评估用独立子进程。

残余非确定性有二：其一，**时钟纪元**——缺省取真实当前时刻的最近 04:00，跨日运行会改变日历相关行为，严格复现必须显式冻结纪元日期；其二，**传输层重试**——桥客户端对失败请求重试一次，对非幂等写操作（推进时钟、换人、无人机）超时后重试可能重复执行。因此确定性命题的完整前提是：**固定纪元 + 无传输层重试触发**。前提成立时，重复运行的 `requestHash`、`traceHash`、`stateHash` 三者一致。

### 6.3 不变量表

以下不变量由代码构造保证，属于结构性质：

| 不变量 | 结论与成立条件 |
|---|---|
| 一人一岗 | 任一干员同一时刻至多占据一个房间槽位；所有占位写入都经唯一占位清理 |
| 房间容量 | 槽位数由排班表与房型决定；宿舍床位等于排班表声明的槽位数，空占位保留为空床 |
| 心情界 | 心情恒在 $[0,24]$：消耗侧双边夹取，回复侧上界夹取，极小正数归零防浮点残留 |
| 订单容量 | 待交付订单数不超过 6/8/10 的等级基线加在岗干员技能加成，满单暂停获取进度；容量下限为 1 |
| 订单生命周期 | 状态只会 pending → delivered；每日 04:00 日刷不清空待交付订单 |
| 仓库容量 | 占用不超过容量上限，满仓停产、收取后恢复；容量 = 12 × 等级 + 技能加成，下限为 1 |
| 无人机上限 | 不超过 250 架，达到上限停止充能 |
| 材料非负 | 碎片批次逐批校验材料与龙门币，不足则冻结进度停产——不产、不扣、不钳零、不负库存 |
| 交付 FIFO | 赤金不足时首笔受阻即停，后续订单留队，不跳单交付 |

容量界的说明：订单容量与仓库容量都是硬上界（结算循环以容量为守卫），不会因步长或操作序列越界；但它们的**数值**是简化模型，与实际运行曲线的偏差属于经验误差，不属于结构缺陷。

### 6.4 适用域与经验误差

当前经验标定覆盖：单一基建布局（2 贸易站 + 5 制造站 + 2 发电站，产物 4 赤金 + 1 经验）、约 138 名干员的暖启动池、设施等级输入正确的前提。在这个范围内做过初步设备侧核对，样本量有限，原始测量数据不随仓库发布。这些结果只说明该适用域内产出量级，不构成跨布局、跨干员池的精度承诺。设施等级输入的正确性尤其关键：输入错误造成的偏差远大于模型本身的误差——先核对排班表声明的设施等级与设备侧记录一致，再怀疑模型。

### 6.5 已知近似与失败模式

以下各条是当前实现的已知边界，按影响方向说明：

1. **仓库容量基线是线性近似**（12 × 等级）；技能加成已接入，基础曲线与实际运行容量不完全一致；
2. **订单档位构成偏差**：哈希选择子不保证服从标称概率分布，表现为"每单金额偏高、订单数偏少"；带加成跑单占比也高于设备侧观测；
3. **跑单换入窗口的效率瞬降为近似**：换入/换回约 1 分钟窗口内被换下干员的技能仍计入效率，估计对订单时序影响小于 2%（本地验收估计，未独立验证）；
4. **非生产房技能未完整建模**：中枢、会客室等房间的部分全局技能尚未进入产量链路；未建模条件族保守判不满足，方向是低估；
5. **训练室专精不建模**：房间与占位存在，专精产出与调度不在仿真范围；
6. **设备耗时取固定值、识别默认成功**：方向是低估失败率与重试耗时；设备侧的 OCR 抖动、误识别、页面卡顿被消除，仿真不能用于评估设备侧稳定性；
7. **交叉校准未收敛**：与另一套独立产出计算引擎的交叉对比仍有约 55% 量级差异，根因指向夹具等级假设与订单/跑单模型口径，尚未逐机制定位完成。差异收敛前，不应把 L1 的绝对产量当作跨引擎一致的结论。

常见失败路径：

| 触发条件 | 表现 | 开发者能做什么 |
|---|---|---|
| 桥服务未启动 | 请求连接失败 | 先 `GET /health`；按 4.1 启动桥 |
| 会话 id 不存在或已关闭 | 404 `session not found` | 重新 `/session` 建会话 |
| 排班表缺 `plan1` | 400 `plan.plan1 required` | 使用 mower 标准排班表格式 |
| 赤金不足 | 首笔订单受阻、后续留队（FIFO） | 补初始库存或等制造产出；这是预期物理行为 |
| 材料不足 | 碎片批次冻结停产 | 同上；不产生负库存 |
| 满仓且未收取 | 制造进度冻结 | `/collect` 收取，或配置自动收取策略 |

### 6.6 结构性质与经验拟合的分界

6.2–6.3 的确定性、守恒等式、容量硬上界、一人一岗、心情界是**结构性质**：由代码构造保证，可顺着公开入口直接验证，不随布局或干员池变化。6.4–6.5 的产量误差、频率对账、档位构成是**经验拟合**：只在已验证适用域内有数据支撑，超出适用域（新布局、新干员组合、活动机制）时误差方向未知，需要重新标定。

## 7 扩展开发与贡献方式

### 7.1 修改物理或技能模型

改动集中在 `ui/src/riic/riic-sim/`：主线物理在 `core/simulator.ts`，数值模块在 `v2/`（心情、订单、技能求值、世界构建各自独立），桥接在 `bridge/`。修改后跑定向测试：

```bash
cd ui
npm test -- --run src/riic/riic-sim
```

这段命令只运行 L1 相关的定向测试（物理、技能求值、容量、心情），不把 UI 全量测试当作 L1 验证。只跑本次改动的相关文件即可。

### 7.2 开发检查清单

- 不引入 `Math.random` 或墙钟读取；
- 新事件有固定阶段位置与时间戳语义；
- 库存变更与事件增量成对写出（守恒等式依赖这一点）；
- 容量、心情、订单生命周期仍满足不变量表（6.3）；
- 新技能条件族未建模时保守判不满足；
- 结构性质变更同时检查不变量对应的代码入口；经验数字变更给出新的测量口径与样本范围；
- 更新"已知近似"或在提交说明中写明原因。

### 7.3 贡献方向

最有价值的贡献是**物理标定**：为 6.5 的已知近似提供公开资料、机制考证或可复现的测量口径（布局、干员池、时间窗、报表来源）。其次是补齐未建模条件族与特殊订单机制的设备侧交叉验证。

## 8 与其他层的关系

- **L2 执行层**消费 L1 的桥端点，把 mower 的真实调度决策转成 L1 的写操作，并把 L1 的状态读回 mower。L1 不知道 mower 的换班与跑单规则；
- **L3 排班优化层**（开发中）设想通过 L2 的评估能力逐候选调用 L1；L1 不感知任何搜索算法，只负责固定输入下的确定性世界。方向见 [L3 目标页](l3-target.md)。

## 9 路线与未完成项

L1 的核心物理与确定性论证已完成，未闭合项集中在数据与校准：

- 低精英等级订单加成数据缺失，相关条目当前按保守规则降级；
- 双 α 订单分布与暖机仍是条件模型（基于转引观测的假设），需要真实观测覆盖；
- 14 天全资源真实对账、赤金/经验分开校准、多 seed 稳定性尚未完成；
- 随机订单分布、初始心情非参考态、部分条件技能族仍是已知缺口。

这些是"校准/数据"问题，不是物理结构缺陷。未闭合前，L1 可用于机制开发与相对比较，不应用于"绝对最优"或跨引擎一致性认证。
