# L2 执行层：让 mower 的真实业务运行在虚拟设备上

> 文档状态：核心可用，接口契约开发中
> 适用版本：closure v0.1.0（上游基线 mower 4.1.6-alpha.15）
> 读者：想无设备跑 mower 业务的开发者；想修改适配层、升级上游或做业务回归的开发者
> 前置知识：mower 的排班表与配置概念；Python 基础；HTTP JSON 调用
> 相关代码：`sim_bridge/`、`sim_api_bridge.py`（Python），公开入口见附录 B

L2 不复制 mower 的调度逻辑，而是在虚拟时钟与运行时替换点（seam）上运行 mower 的真实业务代码：设备操作与读屏被换成对 [L1 仿真层](l1-simulation.md)的调用，决策仍然全部来自 mower 本体。不需要手机、模拟器或 ADB，一份排班表就能跑起完整基建流程。

## 1 这套能力解决什么问题

mower 的基建业务（心情读取、跑单求解、副表切换、轮休规划、任务执行）原本依赖真实设备运行：改一行逻辑要等设备侧跑一轮才知道后果，两次运行不可比，异常场景靠运气。

L2 把"设备"换成 L1 的确定性世界，把"时间"换成可推进的虚拟时钟，于是：

- 完整基建业务无设备运行，日志仍是 mower 真实业务日志的形状；
- 时间可以快进：一次 7 天演算约 2 分钟（本地标定口径，随机器性能变化）；
- 运行可以哈希、回放、差分，业务回归有了可复现的基准。

L2 不负责：基建物理与技能求值（属于 L1）；候选排班搜索与排名（属于 L3，开发中，见 [L3 目标页](l3-target.md)）；修改 `arknights_mower/` 源码（上游零改动是硬约束）。

## 2 你能用它做什么

L2 支持以下开发任务：

1. **无设备跑完整基建流程**：把排班表 JSON 交给 `/mower/start`，mower 的心情读取、跑单求解、副表切换、轮休规划、任务执行就在虚拟世界里跑起来（第 4 章有最小示例）；
2. **快进迭代**：改一行调度逻辑，约两分钟后就能看到它在一周尺度上的后果——轮休是否死锁、跑单窗口是否冲突、副表切换是否抖动。"假设 → 验证"的循环从以天计压到以分钟计；
3. **可复现回放/差分**：一次运行收敛成可哈希的记录，重复运行比较三个哈希即可断言复现；不一致时逐事件定位首个分叉点（7.2）；
4. **业务回归**：改动前后用固定请求集回放，逐指标对比产量、漏单、涣散、任务保留次数；两个执行通道差分还能分离"业务逻辑差异"与"执行路径差异"（7.3）；
5. **CI 三道门**：上游零改动门、契约门、短窗口演算门，把适配层漂移挡在合并之前（7.4）；
6. **调试能力**：运行日志、事件流、状态快照、任务队列四类可观测物；推进是断点式的，可以停在任意一天、任意一小时检查状态再继续（7.5）。

## 3 核心概念与数据流

### 3.1 虚拟时钟

mower 大量使用日历时刻（每日 04:00 刷新、按小时排任务）。L2 用"纪元 + 仿真偏移"构造虚拟时钟，替换 Python 的 `datetime.now`、`time.time`、`time.sleep`：读时间得到仿真时刻，sleep 不真实等待而是累积偏移。替换必须在 import mower 之前完成，且返回的 datetime 实例保持子类身份——mower 内部的类型判断依赖这一点。

`time.monotonic` 保持真实：mower 的防自旋超时语义是"真实耗时上限"，若被仿真时钟污染，毫秒级操作会被误判为超时。真实单调时钟只用于这类保护性判断，不参与调度决策。

时钟协同规则：L1 桥是物理时钟权威。桥写操作返回绝对仿真时刻后，mower 时钟**只向前对齐，绝不回拨**；seam 内的微操作耗时先本地累积，在下次读写前一次性冲刷，避免每个小动作都触发一次 HTTP 推进。本地累积设有风暴熔断：连续未冲刷的空等待超过阈值即抛错，防止识别路径死循环把演算挂死。

### 3.2 seam：替换设备副作用，保留业务决策

seam（缝隙）是运行时替换的 mower 方法/属性：只换"设备介质"，不换业务语义。按语义分三类：

- **精确替换**（语义等价）：读驻员与心情、读订单倒计时、换人、无人机加速、全量心情扫描等，改从 L1 桥读写，保留 mower 的心情簿记、消耗速率学习、预等待减算、加速后重读等决策闭环；
- **近似替换**（默认成功 + 记录耗时）：屏幕导航、识别、点击类操作由虚拟屏幕承接，视为成功并累积设备耗时。误差方向是低估失败率与重试耗时；
- **不替换、原样运行**：任务状态机、跑单求解、副表求解、产物切换排队、心情观测等 mower 入口保持原样。

执行任务时优先驱动 mower 自己的执行状态机，覆盖换班/换入/涣散下岗/宿舍补位与释放/自我纠正/重排单等任务类型；失败或不支持的任务类型回退到适配层自研执行器（直接调桥物理），演算不中断。跑单、切产物、菲亚梅塔充能等任务走自研执行器，避免 mower 的换产物屏幕流程在虚拟设备上中途崩溃。

全部 seam 登记在 `sim_bridge/seam_contract.py` 的注册表，与实际替换一一对应，注册表漂移会被契约检查直接点名。seam 的数量与风险分级是实现细节，不是调用方需要记忆的契约；调用方只需知道：**设备副作用被替换，业务决策原样保留**。

### 3.3 无头调度与会话服务

无头调度器初始化 mower 的真实调度器（mock 设备），禁用非基建 solver（线索、信用、访友、MAA、专精、回收、邮件），只跑基建主流程。mower 的记录库被重定向到临时数据库，每次建会话前清空——仿真未来时间戳不会写进真实记录库。

常驻服务（默认 `:5901`）提供会话生命周期：建会话/接管活跃会话/缓存命中三态、同步推进、后台推进、增量拉取、关闭。推进循环的节拍参数（步长、心情同步、深度规划、快照间隔）是保真度与吞吐的折中，见 6.5 实现取舍。

### 3.4 进程隔离是正确性要求

虚拟时钟替换的是**整个 Python 解释器**的 `datetime`/`time` 模块对象，不是线程局部状态。因此 L2 服务必须运行在独立子进程：

- 源码环境：用仓库 `.venv` 解释器以子进程启动 `python -m sim_bridge.mower_service`；
- 打包环境：用 `mower.exe --sim-service` 启动独立子进程。

把服务作为宿主线程运行会污染 mower 主进程的调度、任务队列与序列化路径，即使短期看起来能跑。多候选评估因此同样使用独立子进程。

### 3.5 数据流

```text
排班表 JSON ──/mower/start──▶ 无头调度器（mower 真实业务 + 虚拟时钟 + seam）
                                    │
        /mower/advance 逐拍推进 ────┤──▶ L1 桥（物理写操作/状态读取）
                                    ▼
        /mower/poll 增量拉取：事件流 / 状态快照 / 运行日志 / 任务队列
```

宿主集成：mower Web 服务（`server.py`）只保留最小注册钩子，`/sim/*` 路由实现在 `sim_api_bridge.py`，同源代理到 L2 服务。首次调用时自动检查并拉起缺席的服务；打包环境不要求用户安装 Node 或 Python 依赖（TS 桥预编译，随包携带运行时；随 v0.1.0 代码发行提供）。

## 4 快速开始（最小可运行示例）

以下命令与路径随 v0.1.0 代码发行提供；当前 docs-only 提交不包含代码。以下命令仅用于本地开发与仿真测试，不构成真实游戏接入教程；不提供 ADB、模拟器、账号或游戏客户端配置步骤。

### 4.1 启动服务

源码环境需要三个进程（L1 桥、L2 服务、宿主可选）：

```bash
cd ui && npx vite-node src/riic/riic-sim/bridge/server.ts   # L1 桥，:5900
```

```bash
.venv/Scripts/python -m sim_bridge.mower_service            # L2 服务，:5901（Windows）
# Linux/macOS 用 .venv/bin/python
```

第一条命令启动 L1 物理世界，第二条启动 L2 执行服务。只跑无设备演算时这两个进程就够了；宿主 Web 服务（`.venv/Scripts/python webview_ui.py`，:58000）提供界面与 `/sim/*` 同源代理，按需启动。打包环境由程序自动拉起这些服务，无需手工启动。

### 4.2 最小无设备演算

以下脚本把一份排班表交给 L2，推进一天，打印库存与执行计数：

```python
import json, urllib.request

BASE = "http://127.0.0.1:5901"

def post(path, payload):
    req = urllib.request.Request(
        BASE + path, data=json.dumps(payload).encode(),
        headers={"Content-Type": "application/json"})
    with urllib.request.urlopen(req, timeout=600) as r:
        return json.loads(r.read())

# 建会话：force=True 忽略旧缓存强制重算；首屏为空，不预演
plan = json.load(open("config/plan.json", encoding="utf-8"))
r = post("/mower/start", {"plan": plan, "force": True})
print("会话:", r["clock"], "cached =", r["cached"])

# 同步推进到第 1 天结束（86_400_000 毫秒）
r = post("/mower/advance", {"toMs": 86_400_000})
print("时钟:", r["clock"])
print("库存:", r["inventory"])
print("执行计数:", r["executed"])   # 换人/跑单/充能等任务的执行次数
```

返回还包含本次增量的事件流、状态快照、运行日志与任务队列。日志是 mower 真实业务日志的形状（完整换班计划、进驻安排、副表演算），不是适配层自造的摘要。

### 4.3 后台推进与增量拉取

长窗口演算转后台，前端按游标增量拉取进度：

```python
# 后台推进到第 7 天（默认目标；上限 28 天）
post("/mower/background", {"toDays": 7})

# 按 ev/snap/log 三游标增量拉取；游标取上次返回的累计长度
r = post("/mower/poll", {"ev": 0, "snap": 0, "log": 0})
print("进度:", r["simMs"], "后台运行中:", r["bg"]["running"])
```

`/mower/advance` 的 `toMs` 传负值也可触发后台推进（按天数计，兼容通道）。演算结束后用 `/mower/stop` 关闭会话。产品界面可按天分段继续推进；API 单次请求仍以 28 天为上限。

## 5 对外契约与稳定边界

### 5.1 服务端点（:5901）

| 端点 | 语义 |
|---|---|
| `GET /health` | 健康与后台状态：`live`、`static`、后台 `running/targetMs/error` |
| `POST /mower/start` | 建会话 / 接管活跃会话 / 缓存命中三态；参数 `plan`、`force`、`initialMoods`、`bridgeUrl` |
| `POST /mower/advance` | 同步推进到 `toMs`（上限 28 天；负值转后台推进，按天数计） |
| `POST /mower/background` | 后台逐块推进到目标天（`toDays`，默认 7 天，上限 28 天） |
| `POST /mower/poll` | 按 `ev` / `snap` / `log` 游标增量拉取 |
| `POST /mower/stop` | 关闭会话 |

返回的公共字段：`simMs`（毫秒时钟）、`clock`（可读时钟）、`inventory`、`executed`、`events`、`snapshots`、`logs`、`tasks`、`counts`、`bg`。建会话不预演，首屏为空，由调用方逐块推进。

### 5.2 宿主同源代理（:58000）

`/sim/start|advance|background|poll|stop` 代理到 L2 `/mower/*`；`/sim/run` 是兼容旧接口（子进程一次性运行，新调用方应使用 start + advance）。同源代理解决实际部署问题：局域网或端口映射访问时，前端直连 `127.0.0.1:5901` 会指向客户端自身而失败；只映射宿主一个端口也能完整使用仿真功能。L1 桥与 L2 服务默认只绑定 `127.0.0.1`，跨机直连需显式配置绑定地址。

### 5.3 会话缓存的对外行为

缓存对调用方表现为三条可观察规则（内部键结构不是契约）：

- 同一排班重复建会话可能直接命中完整缓存（默认 7 天演算结果），`force=true` 强制重算；
- 缓存命中时任务队列为空视图，**不能据此判断"没有任务"**；缓存会话不支持继续扩展天数；
- 初始心情不参与缓存键（真实库心情每次都在变），缓存只记录暖启动元信息，不存档具体心情值。

### 5.4 环境变量

| 变量 | 作用 |
|---|---|
| `SIM_BRIDGE_PORT` | L1 桥端口 |
| `MOWER_SERVICE_PORT` / `MOWER_SERVICE_HOST` | L2 服务端口与绑定地址 |
| `MOWER_SIM_WARM_START=0` | 关闭暖启动 |
| `MOWER_SIM_DEBUG=1` | 恢复 DEBUG 日志 |

### 5.5 版本语义

端点路径与读写语义当前可用，契约仍属开发中、可能微调；上游基线为 mower 4.1.6-alpha.15，升级基线必须走 7.4 的契约检查流程。L3 能力尚未推送，调用方不应依赖任何 L3 端点。

## 6 可靠性、限制与失败模式

### 6.1 确定性前提

L2 的确定性不是无条件的，完整前提是：

- **固定纪元**：虚拟时钟缺省取真实当前时刻的最近 04:00；严格复现必须显式冻结纪元日期（`init_sim_clock(epoch_date)`），不能依赖缺省纪元。公开回放工具 `sim_bridge/mower_sim.py` 当前使用缺省纪元，跨日运行会改变日历相关行为；
- **无传输层重试触发**：桥客户端对失败请求重试一次，对非幂等写操作（推进时钟、换人、无人机）超时后重试可能重复执行；
- **无并发写**：会话服务用全局锁串行化操作，单个会话在单进程内顺序处理；
- **技能数据与配置在运行期不变**。

四个前提成立时，同一请求重复运行的 `requestHash`、`traceHash`、`stateHash` 三者一致；回放差分工具可以逐事件定位两份运行的首个分叉点。

### 6.2 保证、经验值与未验证

- **保证（结构性质）**：上游零改动（契约门强制）；虚拟时钟只向前对齐；真实记录库零污染（记录库重定向）；进程隔离边界内的时钟替换不影响宿主；
- **经验值（本地标定，随环境变化）**：7 天演算约 2 分钟；设备耗时按设备侧 P95 口径取固定常量；识别与点击默认成功，方向是低估失败率与重试耗时；
- **未验证**：推进节拍相对设备侧的保真度尚未全量量化；seam 主要靠离线/mock 设备验证，设备侧覆盖不足；设备侧端到端回归矩阵尚未建立。

### 6.3 失败模式与降级

| 触发条件 | 表现 | 开发者能做什么 |
|---|---|---|
| L1 桥未启动 | 建会话/推进报错 | 先启动桥并 `GET /health`；宿主代理会自动拉起缺席服务 |
| L2 服务启动失败 | `/sim/start` 返回错误并带日志末尾 | 查看安装根目录 `tmp/mower-service.log`；不会无限等待 |
| 打包环境缺少仿真模块 | 宿主打印一行诊断后跳过 | mower 本体照常运行；仿真功能不可用 |
| mower 状态机执行失败/不支持的任务 | 回退自研执行器，演算不中断 | 日志可见回退记录；用双通道差分定位（7.3） |
| 识别路径空等待死循环 | 风暴熔断抛错，演算终止 | 检查 seam 的屏幕状态假设；这是保护机制而非挂死 |
| 桥传输失败 | 客户端重试一次 | 注意非幂等写可能重复执行（6.1）；检查桥日志 `tmp/sim-bridge.log` |
| 缓存损坏 | 自动重算 | 无需干预 |

### 6.4 已知边界

- 缓存命中时任务队列为空视图；缓存会话不支持扩展天数；命中要求演算已完整（达到默认 7 天目标），不足 7 天的逐日落盘缓存重启后不会被当作静态会话加载；
- 暖启动心情来自真实记录库，跨次运行可能不同；严格复现需显式传入 `initialMoods` 或关闭暖启动；
- 非基建 solver（线索、信用、访友、MAA、专精、回收、邮件）被禁用，只跑基建主流程；
- 传输层重试对非幂等写可能重复推进时钟。

### 6.5 实现取舍（内部节奏参数）

以下参数是保真度与吞吐的折中，属于实现细节，调用方不需要记忆，也不应依赖其精确值：

- 推进步长 60 秒；每 45 分钟全量心情同步（含宿舍与板凳）——只读工作房会让宿舍床位状态过期、轮休卡在稳态，且 mower 的消耗速率学习要求同一岗位两次实读间隔超过 29 分钟；每 5 分钟深度规划（跑单求解、副表求解、产物切换排队）；每 10 分钟状态快照；
- mower 真实状态机单任务上限 60 步、真实耗时 5 秒防自旋；
- 缓存键为排班文档与缓存语义版本的哈希前缀，缓存目录为安装根目录的 `tmp/sim-cache/`；每跨过一个仿真天原子落盘一次，不允许更短的新会话覆盖更长的旧缓存；语义模型变更时提升缓存版本，旧缓存自动失效；日志游标用单调递增序号，环形缓冲截断后增量拉取依然正确。

这些节奏尚未与设备侧节奏做全量量化（见第 9 章路线）。

## 7 扩展开发与贡献方式

### 7.1 修改 seam 与升级上游

seam 注册表、数据契约（必需任务类型、排班模型字段、干员数据属性、资源文件格式）与上游关键文件的哈希基线都登记在 `sim_bridge/seam_contract.py`。升级上游是一条命令链：

```bash
# 1. 同步上游代码后，先跑静态契约检查（秒级，不需要桥在线）
.venv/Scripts/python -m sim_bridge.compat_check

# 2. 按报错点名修复适配层（不改 arknights_mower/），再跑短窗口演算验收
.venv/Scripts/python -m sim_bridge.compat_check --smoke   # 附加 1 小时仿真冒烟，需桥在线

# 3. 验收通过后刷新基线
.venv/Scripts/python -m sim_bridge.compat_check --record
```

第一步静态检查契约与基线差异；第二步附加小时级冒烟确认行为；第三步固化新基线。`--json` 输出机器可读结果。新增或修改 seam 时同步更新注册表，漂移会被契约检查直接点名。

### 7.2 构造可复现运行（回放/差分）

`sim_bridge/mower_sim.py` 把一次运行收敛成可哈希、可差分的记录。请求示例（保存为 `req.json`）：

```json
{
  "planPath": "config/plan.json",
  "conf": {"drone_count_limit": 90},
  "initialInventory": {"gold": 1000, "lmd": 100000, "exp": 0},
  "initialMoods": null,
  "windowMinutes": 120,
  "executor": "transition",
  "coreOptions": {"autoCollect": true}
}
```

这份请求固定了复现身份的主要输入：排班、配置差异、初始库存、初始心情、窗口与执行通道；引擎版本与 trace 版本见下方要点。运行两次并比较：

```bash
.venv/Scripts/python -m sim_bridge.mower_sim replay --request req.json --out run-a.json
.venv/Scripts/python -m sim_bridge.mower_sim replay --request req.json --out run-b.json
.venv/Scripts/python -m sim_bridge.mower_sim diff --a run-a.json --b run-b.json
```

`requestHash`/`traceHash`/`stateHash` 三者一致即复现成立；不一致时输出首个分叉事件的序号与内容。要点：

- 复现身份由输入闭合：排班、conf、初始库存、初始心情、窗口、执行器、引擎版本与 trace 版本全部进 `requestHash`；
- conf 是 overlay：只传差异字段，白名单校验，注入失败显式报错，不静默退回磁盘配置；
- 日志文本与墙钟耗时不进哈希：运行耗时波动不破坏复现判定；
- 纪元：该工具当前用缺省纪元（最近 04:00），不把纪元日期写入身份哈希；严格跨日复现需自行固定纪元。

### 7.3 业务回归

`executor: "transition"` 驱动 mower 真实执行状态机，`executor: "custom"`（或环境变量 `MOWER_SIM_EXECUTOR=custom`）强制走自研执行器。同一排班在两个通道下回放并差分，可以分离"业务逻辑差异"与"执行路径差异"。改动业务相关代码后，用固定请求集回放前后版本，逐指标对比产量、漏单、涣散、任务保留次数。

### 7.4 CI 三道门

1. **上游零改动门**：`git diff --exit-code -- arknights_mower` 必须为空；
2. **契约门**：`python -m sim_bridge.compat_check --json`（静态检查，秒级，不需要桥在线）；
3. **短窗口演算门**：启动桥后跑 `--smoke` 小时级冒烟或固定请求回放，断言无执行器错误、无任务丢弃。

### 7.5 调试能力

一次运行留下四类可观测物：

- **运行日志**：仿真时间戳、单调序号、源文件与函数名；
- **事件流**：物理事件 + 任务派发/完成/错误；
- **状态快照**：逐房效率、驻员心情、订单倒计时、库存、电力；
- **任务队列视图**：当前任务与保留状态。

推进是断点式的：`/mower/advance` 接受任意目标时刻，可以停在任意一天、任意一小时检查状态，再继续。回放工具的 trace 分 all/none 两档（all 含事件、任务与状态快照，none 只留指标），长窗口可按需裁剪。

### 7.6 mower-sim：面向业务核心开发者的工作台

mower-sim 是 L2 的衍生开发工具，不是新的架构层。它面向 mower 业务核心开发者，不面向普通用户：不接设备，快速试错、复现 bug、优化核心逻辑、做回归。

四类使用场景：

- **快速试错**：改一处调度逻辑，分钟级看到一周尺度的后果；
- **复现 bug**：固定排班、配置、初始库存与心情，重复运行到同一现场；
- **最小化失败**：把长窗口运行裁剪成更短的失败序列；
- **批量回归**：用固定请求集回放前后版本，比较产量、漏单、涣散、任务轨迹。

当前状态：最小回放工具 `sim_bridge/mower_sim.py` 随 L1/L2 代码发行提供，支持 replay、diff 与 request/trace/state 三层哈希（用法见 7.2）。当前可用的是命令行回放工具；mower-sim 前端/可视化工作台尚未提供，计划在后续版本发布。完整 mower-sim（批量运行、失败最小化、fuzz、静态门禁、健康报告等）仍在开发，尚未随公开源码发布。

边界：L1 提供确定性物理世界，L2 提供无头执行、虚拟时钟、seam 与会话；mower-sim 是 L2 之上的开发/调试工作台。它不替代 L3 的候选评估与排名，结果也不当作 L3 认证，也不替代设备侧验收。

mower-sim 不修改 `arknights_mower/` 源码，不模拟设备硬件、OCR 噪声和用户中间状态，不承诺“绝对最优”。它的结果是开发与回归依据，不是认证结论。

## 8 与其他层的关系

- **L1 仿真层**提供世界状态与物理写操作；L2 不推导物理，只调用桥端点并读取结果。L1 的适用域与经验误差见 [L1 文档](l1-simulation.md)第 6 章；
- **L3 排班优化层**（开发中）设想通过 L2 的评估能力跑候选排班，每个候选使用独立子进程以避免虚拟时钟污染；方向见 [L3 目标页](l3-target.md)，接口与实现尚未推送。

## 9 路线与未完成项

- 量化推进节拍（步长、心情同步、深度规划、快照间隔）相对设备侧的保真度；
- 扩大 seam 的设备侧覆盖，建立漂移检查常态化；
- 补设备侧端到端回归矩阵，覆盖执行异常与恢复路径；
- 为接口增加契约版本与快照格式哈希，稳定缓存身份；
- 补任务失败/调度循环契约的离线测试；
- 按后续需求逐步放开被禁用的非基建 solver，不一次性全开。

## 附录 A 术语

| 术语 | 含义 |
|---|---|
| L2 执行层 | Python 无头适配层，让 mower 真实业务在虚拟时钟与 seam 上运行 |
| seam | 运行时替换的 mower 方法/属性缝隙：只换设备介质，不换业务语义 |
| 虚拟时钟 | 纪元 + 仿真偏移；只向前对齐；真实单调时钟仅用于防自旋保护 |
| 无头调度器 | mower 的真实调度逻辑 + 桥提供的状态读取与操作能力 + 可推进循环 |
| 暖启动 | 用真实记录库的最近心情作初始状态，避免全员满心情造成同步涣散波 |
| requestHash / traceHash / stateHash | 回放复现身份：输入 / 确定性轨迹 / 终态的内容哈希 |
| 双通道执行 | mower 真实状态机优先，自研执行器兜底；两通道可差分对比 |
| 同源代理 | 宿主 `/sim/*` 路由转发到 L2 服务，解决局域网直连指错机器的问题 |
