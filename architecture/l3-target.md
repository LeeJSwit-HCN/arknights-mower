# L3 排班优化层：目标与设想

> 相关代码：尚未推送

L3 是仿真环境下的排班评估研究，不是《明日方舟》官方功能，也不提供真实游戏接入。

## 1 为什么需要 L3

有了 L1 的确定性基建世界与 L2 的无头执行，"哪张排班表更好"第一次可以在不依赖设备侧的前提下被反复评估。但评估本身不等于优化：

- 人工试排班靠经验，难以系统比较大量候选；
- 设备侧评估慢且不可复现，无法支撑逐候选评分；
- 即使仿真可复现，若评估身份不固定，分数差异仍可能来自运行时序而非排班本身。

L3 希望把"排班好不好"变成一个可重复、可比较、可归因的问题：在固定评估条件下对候选排班做确定性评估，让分数差异真正反映排班差异。

## 2 方向性目标

以下是方向设想，不是承诺，也不是现有能力：

- **确定性评估**：同一候选在固定输入与评估身份下重复评估，结果一致；
- **候选排班比较**：多份候选排班在同一口径下评估，提取可比较的指标；
- **指标与排名**：从评估结果折算指标并排名，输出当前找到的较优候选及其指标；
- **差异可归因**：评分差异归因到排班本身，而不是设备噪声、运行时序或初始状态漂移。

## 3 与 L1/L2 的关系

- **L1 仿真层**提供确定性物理世界。L3 不改写 L1 的物理，只依赖其在固定输入下的可复现输出；
- **L2 执行层**提供无头执行与进程隔离。L3 设想通过 L2 的评估能力逐候选运行，每个候选在独立进程中评估，避免虚拟时钟污染；
- L3 是 L1/L2 之上的消费方：把下层已经提供的"可复现评估"组织成"可比较的排班优化"，不反向修改下层的物理或执行逻辑。

## 5 边界与不承诺

- 不把任何候选标成"已认证最优"：真实数据校准与审计完成前，只谈相对比较，不谈绝对最优；
- 不承诺跨布局、跨干员池、跨账号的绝对产出；
- 不提供真实设备或真实账号的接入支持；
- 不放宽 L1/L2 的确定性与进程隔离约束来换取优化效果；
- 评估结论的可信度依赖 L1 的适用域与 L2 的确定性前提；超出适用域或前提不成立时，只能给出"该次运行中更好"的结果，不能给出可比较的排名。
