# closure 分支分层文档导读

> 文档状态：稳定
> 适用版本：closure v0.1.0
> 读者：熟悉 Python/TypeScript、用过 mower，第一次接触 closure 分支的开发者
> 前置知识：mower 的排班表与基建业务概念

本目录是 closure 分支的软件工程、仿真与测试研究文档，不构成对任何游戏服务条款的合规意见，也不提供真实游戏接入教程。

closure 分支不修改 mower 的基建业务，而是给这套业务补上三层能力：一个可复现的基建世界（L1 仿真层）、一个让 mower 真实业务在其中运行的执行层（L2 执行层），以及正在开发中的排班优化方向（L3）。

## 1 closure 为什么存在

mower 的基建业务原本依赖真实设备运行，有三个绕不开的限制：

- **评估慢**：想知道一张排班表 7 天的产出指标，就要真的等 7 天；
- **结果不可比**：OCR 噪声、设备卡顿、运行时噪声，让前后两次运行无法直接对比；
- **异常难构造**：满仓、断供、跑单窗口错过、干员涣散，只能靠运气遇到。

closure 把这三个问题拆开处理：L1 提供确定性的基建物理，在固定纪元且无传输重试的前提下，同样的输入得到同样的结果；L2 让 mower 的真实调度逻辑在虚拟设备上原样运行，不需要手机、模拟器或 ADB；L3（开发中）希望在这两层之上，对候选排班做可复现的比较与排名。

L3 是仿真环境下的排班评估研究，不提供真实游戏接入。

业务改动可以在分钟级看到一周尺度的后果；回归可以用固定输入反复回放；异常场景可以主动构造。

## 2 三层各解决什么问题

```text
┌──────────────────────────────────────────────────────────────┐
│ L3 排班优化层（开发中，敬请期待）                               │
│   目标：候选排班 → 确定性评估 → 指标与排名                      │
├──────────────────────────────────────────────────────────────┤
│ L2 执行层  sim_bridge/（Python）                               │
│   虚拟时钟 / 设备操作替换（seam）/ 无头调度 / 会话与缓存        │
├──────────────────────────────────────────────────────────────┤
│ L1 仿真层  ui/src/riic/riic-sim/（TypeScript）                 │
│   基建物理 / 技能求值 / 定步长推进 / 事件记录                   │
└──────────────────────────────────────────────────────────────┘
宿主集成：mower Web 服务（server.py）
  └─ 注册钩子 → sim_api_bridge.py（/sim/* 同源代理）
```

| 层 | 解决什么问题 | 当前状态 | 文档 |
|---|---|---|---|
| L1 仿真层 | 给定排班与操作，确定性地回答"接下来物理上会发生什么" | 核心稳定，校准未闭合 | [L1 仿真层](l1-simulation.md) |
| L2 执行层 | 让 mower 真实业务无设备运行：虚拟时钟、设备替换、会话服务 | 可用 | [L2 执行层](l2-execution.md) |
| L3 排班优化层 | 对候选排班做确定性评估与排名（方向） | 仍在开发中，尚未推送 | [L3 目标页](l3-target.md) |

层与层之间通过 HTTP JSON 连接：L1 桥默认端口 `5900`，L2 常驻服务默认 `5901`，mower Web 服务默认 `58000`。浏览器与外部调用方经宿主的 `/sim/*` 同源代理访问，局域网或端口映射场景只需暴露宿主一个端口。

## 3 三条设计原则

1. **上游零改动**：`arknights_mower/` 不做源码修改，所有适配发生在 L2 的运行时替换里；`git diff --exit-code -- arknights_mower` 必须为空。升级上游时先跑契约检查，再按点名修复适配层。
2. **决策与物理分离**：L1 只跑物理，何时换班、跑哪一单、无人机投给谁，全部由 mower 本体在 L2 中决策。仿真不复制、不改写业务逻辑。
3. **可复现优先、失败可降级**：L1 不读墙钟、不用未播种随机；L2 的虚拟时钟只向前对齐；任一层失败不拖垮 mower 本体，降级代价在对应层文档中说明。

## 4 读者路径

**想用仿真做业务回归**：读 [L2 执行层](l2-execution.md) 的快速开始，无设备跑起一份排班表；再用回放与差分构造可复现回归。遇到产量数字疑问时，回查 [L1 仿真层](l1-simulation.md) 的适用域与已知限制。

**想改 L1 物理或技能模型**：读 [L1 仿真层](l1-simulation.md) 的核心概念与可靠性论证，弄清结构性质与经验拟合的分界；改动后按该文档的扩展开发章节跑定向验证。

**想改 L2 适配层或升级上游**：读 [L2 执行层](l2-execution.md) 的 seam 机制与升级护栏；先跑契约检查，再跑短窗口演算验收。

**关注 L3 方向**：读 [L3 目标页](l3-target.md)，了解目标与边界。L3 仍在开发中，尚未推送，当前不提供任何可用接口。

## 5 文档状态与阅读约定

文档按读者任务组织：先讲问题与用法，再讲契约与原理，内部实现细节放附录。阅读约定：

- 代码引用只写路径与符号名，不写行号；
- 文档以中文为准；
- 公开文档不含内部研究、技术债与未公开设计。

| 标记 | 含义 |
|---|---|
| 稳定 | 接口、数据格式或核心行为已冻结，变更需兼容性说明 |
| 开发中 | 可用但契约可能调整 |
| 未验证 | 有实现但缺真实数据或认证 |
| 目标页 | 尚未落地、只公开方向，状态固定"正在开发，敬请期待" |

同一篇文档可以混合多种状态（如"核心稳定、校准未验证"），状态行会写清范围。层号是稳定标识：L1 仿真层、L2 执行层、L3 排班优化层；代码目录名与历史文件名中的旧编号不因文档分层调整而重命名。

文档中的经验数字来自开发者本地标定，测试与验收数据不随仓库发布；引用时以文档标注的适用域为准。

## 6 上游同步与更新器

Closure 基于上游 `v4.1.6-alpha.15` / `f7b1a70` 固定派生，不自动跟随 alpha 的最新推送，也不自动跟随每个 tag。上游变更作为同步检查点，由维护者审计后再合并；合并前运行 seam 契约检查、L1/L2 定向测试与打包验收。

Closure 0.1.0 禁用继承自上游的自动更新器，避免被上游 Release/Nightly 或源码分支覆盖。后续版本将提供 Closure 自己的更新器。
